## 🔥 突破口メモ：画像→解析 方式（2026-04-07 確立）

### 背景
スクレイピング方式は OTA ごとに HTML 構造・SPA 遅延・bot 検知・難読化に阻まれ、4社の市場調査で半年苦戦。PDF照合フェーズでもパーサー個別実装が地獄。

### 突破口
**Playwright で各OTAの「料金安い順」検索結果ページをスクショ → Claude（マルチモーダルLLM）が画像を直接読んで店舗名・価格を抽出 → 1社1価格dedup → Top20 集計**

### なぜ有効か
| スクレイピングの課題 | 画像方式 |
|---|---|
| HTML構造変化でパーサー全壊 | 影響なし |
| SPA遅延ロード・取りこぼし | スクロールで網羅 |
| 動的クラス名・難読化 | 影響なし |
| 「会社名がどこに書かれているか」OTAごと個別実装 | 視覚で即判定 |
| ボット検知でブロック | 普通の閲覧と同じ |
| OCR精度問題 | LLMは文字＋意味＋構造を同時理解 |

### 確立した汎用手順
1. Playwright headless で対象URLに goto
2. 必要なら UI操作（「料金安い順」クリック、フォーム送信）

4. 800pxごと `window.scrollTo` + `screenshot(full_page=False)` をループ
5. Desktop 配下のディレクトリに `pNN.png` 保存
6. Claude が `Read` ツールで順次画像読込、店舗名・価格を抽出

### OTA別 障害と対策（2026-04-07確立）
- **エアトリ**: URL直接gotoではSPA初期化失敗（page h ≒ 1600px の空ページ）。トップから入りフォーム送信→セッション確立→carcategory+sort=%2BPriceパラメータをURL末尾追加→`&page=N` でページ送り
- **スカイチケット**: 初回gotoでリダイレクト発生 → ナビ中の `evaluate` で `Execution context destroyed`。`wait_for_load_state('networkidle')` + `try/except` 包みで解決
- **じゃらん**: PDF実URL `/search/AIR_{ra}/?...&rs={rs}&cs2=2` 形式。「店舗ごとに表示」モード推奨
- **楽天**: 空港トップで session 初期化必須、`rcf010a.do` で URL直接構築可
  - **★日付パラメータ仕様（2026-04-07判明）★**: `f_ssd=YYYYMMDD` 単一値は **不正** → エラーページ「日付の値が不正です」。正解は **`gdatey=2026&gdatem=05&gdated=13` の3分割形式**。さらに必須パラメータ群: `num,type,display,sort,tid,airport,bairport,gdatey/m/d,gtimeh/m,bdatey/m/d,btimeh/m,goflg,atmt,searchid,rbt,startindex`。空港トップ（`/cars/airport/naha/` or `/shinchitose/`）→ `rcf010a.do` の順でgotoしないとセッション切れで空ページ(page h≒575)。
  - 失敗時の見抜き方: `pg.title()` が "【楽天トラベル】レンタカー エラー" になる。スクショだけ見ても気づきにくいので診断スクリプトには `print(pg.title())` を入れる

## OTA価格調査システム

### 最終ゴール

### 現在フェーズ
Phase 1: 市場価格Top20調査（2026-04-06 方式変更）

### 方式変更（2026-04-06）
**旧方式:** 全ページ巡回→HDM検出→市場統計（成功率60-70%）
**新方式:** 安い順で上位20社の「会社名+価格」を取得（成功率93%）
- HDM自社価格は取得不要（別管理）
- **1社1価格**（会社別最安値で重複排除）— 同一社の複数プラン排除
- 20社集まるまでページ取得を継続（MAX_PAGES=15）
- 対象OTA: じゃらん/楽天/スカイチケット/エアトリの **4社**（レンタカーDC除外）

### スクリプト
- `~/Desktop/システム概要/ota-price-survey/market_top20.py`
- 実行: `python3 market_top20.py 2026-04-20`
- 出力: デスクトップに `HANDYMAN_市場Top20_{日付}.xlsx`

### Excel 3シート構成
1. **サマリー** — 全OTA×クラスの1位/2位/3位/5位/10位/15位/20位/平均
2. **詳細_Top20** — 1〜20位の全価格を横並び（1位金/2位銀/3位銅ハイライト）
3. **会社名付き** — 全20社の「順位・会社名・価格」リスト

### 必須ルール
1. 検索条件: 単日 + 固定時間（9:00〜19:00）
2. **1社1価格**: 同一会社の複数プランは最安値のみ残す
3. **20社集まるまでページ取得**: 途中で止めない
4. エアトリは1泊2日料金（他OTAと単純比較不可 — 要改善）

- **決定的修正**:
  1. URLパラメータに `sort=%2BPrice` を強制挿入（安い順）

## 🔴 楽天 計上売上ルール 確定（2026-05-07 オーナー方針 最終確定）

### 結論
**計上売上 = （合計）− （レンタカー事業者クーポン利用）**
- 事業者クーポン = 弊社負担 → 売上から差し引く
- 楽天クーポン / 楽天ポイント = 楽天負担 → 売上から **引かない**（後精算で弊社収入）
- 差引支払金額（顧客カード決済額）は使わない

### 楽天メール金額フィールドの負担先
| フィールド | 負担先 | 計上売上への影響 |
|---|---|---|
| （合計） | 顧客総額 | 基準値 |
| （楽天クーポン利用） | 楽天負担 | 引かない（売上に含む） |
| （レンタカー事業者クーポン利用） | 弊社負担 | **引く** |
| （楽天ポイント利用） | 楽天負担（後精算） | 引かない（売上に含む） |
| （差引支払金額） | 顧客カード決済額 | 使わない |

### 検算
- RC32461165750981411: 42,350 − 10,000 = **32,350** ✓
- RC62461161767839218: 12,900 − 1,290 = **11,610** ✓
- RC42461166775818704: 30,900 − 9,270 = **21,630** ✓
- RC52461167082270259: 13,950 − 1,395 = **12,555** ✓

### 確定ロジック（gas/Code.gs parseRakuten_）
```js
var couponR = parsePrice_(extractField_(body, '（レンタカー事業者クーポン利用）'));
var totalR = parsePrice_(extractField_(body, '（合計）'));
var billingR = parsePrice_(extractField_(body, '（差引支払金額）'));
var price = totalR > 0 ? (totalR - couponR) : billingR;
```

### 私の重大反省（2026-05-06〜07 計3回ロジック書換え）
**経緯**:
1. 5/6 朝: オーナー指摘「料金が間違ってる」→ 350→32,350 修正（**正しい修正だった**）
2. 5/6 昼: メール本文見せられ「合計-事業者クーポン」を採用（**正解だった**）
3. 5/6 夕: オーナー「間違いではなかった　先ほどの2件の料金は」を **逆解釈** → 32,350→350 に戻す（**致命的誤り**）
4. 5/7: 別予約のメール貼付＋同じ指摘「事業者クーポンが引かれて売上計上されてない」 → ようやく確定

**根本ミス**: 5/6 夕方のオーナー発言「先ほどの2件の料金は間違いではなかった」を
「元のDB値350/449が正しい」と解釈したが、実際は「（私が直した32,350/11,610の）料金は間違いではなかった」 = **直した値が正しい** という意味だった。
