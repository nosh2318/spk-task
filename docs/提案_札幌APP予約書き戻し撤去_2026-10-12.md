# 札幌APP「DBに無い予約を書き戻す」処理の撤去案（2026-10-12・未実施／オーナー判断待ち）

## 1. いま何が起きているか（コードと audit_log で確定）
対象は札幌スタッフAPP（`index.src.html`）だけ。那覇・高松のAPPにこの処理は無い（grep で 0 件）。

| # | 場所 | 動き | 結果 |
|---|---|---|---|
| A | silentRefresh（23420行付近）`if(bk.length>useRes.length)useRes=bk` | 端末のバックアップ（localStorage `spk_reservations_backup`）の件数がDBより多いと、DBではなくバックアップを表示に使う | DBで消した予約が画面に戻る（DBには書かない） |
| B | silentRefresh（23430〜23440行）`localOnly` → `DB.upsertReservations([lr])` | 「画面にあるがDBに無い予約」を「保存前の手動追加」とみなし、行全体をDBへ再保存（`changed_json={"_src":"system"}`） | **DBで消した予約がDBに復活**（ゾンビ） |

- 復活の実績（audit_log・7/6〜10/12）：**36予約・85回**。すべてテスト・デモ・オーナーの試験予約で、お客様の予約は無し。
- うち **スタッフAPPで消した予約の復活が6件**（HDMS2609152083/155447/155457/156418/158710・ZZNOTICEMAIL0814）。人間の削除も戻せるので、実予約でも起き得る。
- 9/27 に一括削除した30件は、9/28 18:18:40 に1台の端末から一斉に復活した（古いバックアップを持った端末）。
- 今も「確定」で残っている復活予約が6件ある：DEMOMYPAGE-SPK／KD-DEMO-KEYDROP／ZZNOTICEMAIL0814／ZZMP-SPK-A／dfghjkl／HDMS2608279463（掃除は別途オーナー判断）。

LEDGER-ONE の「ゾンビ復活」と同じクラス（端末の古い写しが正本を上書きする）。

## 2. 撤去案（1デプロイ・SPK v4.7.667）
原則：**DBが正本。端末は表示するだけ。端末から書くのは、その端末で人が行った操作の1件だけ**（グローバル §3）。

1. **B を撤去**：silentRefresh から `localOnly` の再保存（`DB.upsertReservations`）を削除する。silentRefresh は予約を一切書かない。
2. **A を撤去**：DBの取得に成功したら、件数にかかわらずDBの結果を表示に使う。バックアップを使うのは、DB取得が失敗・0件のとき（＝オフライン時の起動）だけ。これは起動時（init）と同じ扱いにそろえる。
3. **手動追加が保存前に消えない保証**（Bが守っていたものの置き換え）：
   - 新設：端末内の「未保存キュー」（localStorage `spk_pending_res`）。入るのは、**その端末で人が追加・編集し、DB保存が3回とも失敗した予約だけ**（addReservation の saveRes 失敗時、bulkAdd 失敗時）。
   - silentRefresh は、DBの結果に**キュー内の予約だけ**を重ねて表示する（キューに無い「DBに無い予約」は表示しない＝ゾンビは出ない）。
   - キューの予約は再送する。1件ずつ（1アクション＝1件）、30分以内のものだけ自動で再送する。成功したらキューから外す。30分を過ぎたものは自動では送らず、画面上部に「⚠️ 未保存の予約 N件（再送／破棄）」を出してスタッフが選ぶ。
   - 再送の前に、その予約番号がキャンセル台帳（`reservation_cancel_ledger`）に削除・キャンセルとして記録されていないかを確認し、記録があれば送らない（別の端末や人が消したものは戻さない）。
4. 変えないもの：起動時の「DBが0件ならバックアップで起動」、リアルタイムの削除反映、`_block_cancel_revival`（キャンセルの復活止め）、LICTEST の INSERT ガード（応急処置として残す）。
5. `manual.html` に、同じコミットで「未保存の予約が出たときの対処」を1行足す。

## 3. 影響範囲（洗い出し）
- 書込経路：silentRefresh（撤去）／addReservation・bulkAdd（失敗時にキューへ入れるだけ・成功時は今と同じ）。CSV取込・場所反映・予約編集の保存は変えない。
- 読込側：予約一覧・タスク（generateTasks は予約から作る）・配車表・OPシート。いずれも表示の元が「DB＋未保存キュー」になる。DBにある予約の見え方は変わらない。
- 他端末：古いバックアップを持った端末があっても、DBに書き戻さなくなる。表示もDBに合わせて次の更新で消える。
- 那覇・高松：該当処理なし＝変更なし。

## 4. 確認手順（デプロイ後すぐ・qa アカウントで本番）
1. 管理SQLでテスト予約（LICTEST以外の試験用id）を作る→スタッフAPPを開いたまま、DBから削除→5分待ってもDBに戻らない（audit_log に INSERT なし）・画面からも消える。
2. 手動追加をネット切断状態で行う（保存失敗を再現）→「未保存 1件」が出て予約は画面に残る→回線を戻すと1回だけ保存される（audit_log の INSERT が1件）。
3. 通常の手動追加・キャンセル・予約編集が今までどおり保存される。
4. 試験予約は、キャンセル→削除→数分後に復活が無いことまで確認して完全削除。
